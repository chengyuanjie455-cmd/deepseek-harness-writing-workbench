# Codex 故障处理

提供报障、完整关联证据、Codex 诊断、原回执恢复和隔离源码修复。成员原生聊天、视频生成模型与权限保持现有逻辑。代码修复经过独立验证后等待更新，不自动覆盖正式应用。

## 入口与状态

- 页面底部“报告问题”不依赖聊天模型，也不依赖原生 iframe 成功启动。
- 原生智能体新增 `team_report_issue`，可把成员明确的软件故障关联到实际调用者和当前会话。普通补抽、改剧情仍走原工具。
- 报告按服务器、成员、项目和会话保存；同一请求重发返回同一回执，不跨聊天合并。
- 页面刷新后仍可查看原报告；断线时使用 IndexedDB 保留正文及可选截图/日志，恢复后按原编号补送。初次打开就无法连接、尚未取得服务器和登录身份时，不能保证跨刷新保存，因此不可假称已送达。
- 后台“运行与审计 → 问题处理”汇总状态、证据索引、Codex 会话、修复记录和一次性执行设置。
- 状态依次为已收到、诊断、恢复原任务、主机原片检查、等待成员聊天端自动加载检查、恢复完成。代码修复通过测试后停在“尚未更新应用”。模型说成功不会直接标记完成。

## 完整上下文的范围

首次报障建立独立快照；补充说明、恢复后的检查另建快照，原快照保留。

| 文件 | 保存内容 |
| --- | --- |
| report.json | 成员说明、项目/成员/会话、客户端状态、所选附件 |
| native-chat.json | 原生 header、全部保存事件、继承事件计数、版本；不使用只读页面的最近 50/100 条分页结果 |
| records.json | 关联会话、任务、模型调用、生成方案、最终提示词、参数、回执、轮次、媒体检查和上传记录 |
| audit.json / events.json | 关联对象全部现存审计和进度事件 |
| updates.json / actions.json | 历次说明、处理进度及恢复动作 |
| attachments.json / attachments/ | 已关联的原生附件、项目上传、资产和成片快照；保存来源及 SHA-256 |
| environment.json / startup-error.json.json | 应用包信息、当前流程配置、项目、主机资源、启动阶段和脱敏异常 |
| manifest.json / summary.json | 索引、条数、时间、哈希与缺口；便于先看摘要再按需读取原件 |

“完整”指登记关联范围内已有证据全部采集成功。旧版丢失的日志、没有登记会话编号的模型调用、旧版已截断的时间线、未落盘事件、缺失附件不能补造，会列为缺口。不会为了凑齐报告把同成员其他聊天或其他成员全部聊天混入。

结构化密钥字段、已知保存密钥、认证头、令牌及签名 URL 会脱敏；文本日志也做替换。图片、PDF、视频等二进制创作资产保持原件，没有实现 OCR 密钥遮挡，不能声称任意截图内容都已脱敏。

## Codex 与恢复执行

1. 仅有故障时启动 `codex exec --json`，绑定明确 thread ID，继续时使用该 ID，绝不使用 `--last`。
2. 明确设置 workspace-write、禁用自动继承个人 config/rules；通过专用配置目录使用既有登录。stdin 传提示词，参数数组启动进程，不用 shell 拼接。
3. 日志中的暂时重连提示可以保留；以进程退出、turn 完成、结构化结果和独立验收共同判断。超时、取消、无效结果均不冒充成功。
4. 生成恢复只接受证据包内、归属匹配的原任务。视频继续原回执的轮询/下载/检查，图片恢复已有回执的下载。提交结果未知时不会新建付费生成。
5. 接受恢复请求不等于成功。主机验证原成员读取权限、文件哈希、视频解码/时长或已有图片技术检查，然后由原成员聊天端自动报告是否能加载。
6. 代码修复只发生在 `incident-repairs/<id>/source`。原代码基线保存在宿主记录中；智能体改写副本里的 baseline.json 不能绕过核对。
7. 独立验证器使用本机已存在的固定 Docker 镜像：无网络、无主机凭据、只读候选挂载，临时空间内运行检查；声明的原回归测试不能被改写。当前源代码变化或测试未通过均停止。
8. 通过后生成改动清单和验证记录，停在等待更新。没有写入应用包、替换服务或自动重启的代码路径。

## 后台自动触发

复用原生持久化索引提取 `turn/end` 的 error 事件；按不同终止事件计数，同一事件的重复轮询只计一次。继承的父会话事件、取消、普通工具文字和创作反馈不计入。开关启用前的历史错误不集中触发。

本版是成员报障为主，原生失败为补充。还不是全面的供应商/系统异常检测器；首次故障归并后的复发窗口、多个成员共因合并、独立于业务主机的常驻守护进程属于后续工作。业务主机整体停机时，浏览器只保留未送达报告，不显示正在修复。

## 主机配置

普通入口与桌面主机入口统一读取数据目录中的 `incident-config.json`，也可以通过 `PLATFORM_INCIDENT_CONFIG` 指向管理员维护的 JSON 文件，示例：

```json
{
  "sourceRoot": "/absolute/path/to/development/source",
  "enabled": false,
  "concurrency": 1,
  "codex": {
    "command": "/absolute/path/to/codex",
    "home": "/absolute/path/to/maintenance-codex-home",
    "timeoutMs": 600000
  },
  "verification": {
    "docker": "/absolute/path/to/docker",
    "image": "your-prepared-verification-image:fixed-version",
    "dependenciesInImage": "/opt/project/node_modules",
    "trustedPaths": ["tests"],
    "commands": [
      ["node", "node_modules/typescript/bin/tsc", "--noEmit"],
      ["node", "node_modules/tsx/dist/cli.mjs", "--test", "tests/targeted-regression.test.ts"]
    ]
  }
}
```

镜像和 Linux 依赖需由主机管理员预先准备；执行器不会自动拉取镜像、安装插件或猜测验证命令。示例中的目录/镜像名不能原样用于生产。

当前 Codex 写沙箱不等于完整主机读隔离。生产启用前应给维护进程使用专用系统账号或容器/虚拟机，仅挂载所需源码、证据和受控登录，不授予任意主机目录读取能力。本次真实验证只传入临时算术函数故障和测试资料，没有读取真实成员聊天交给 Codex。

## 验证与边界

- `tests/incidents.test.ts`：8 人 × 3 会话、完整 350 条事件、附件、去重、脱敏、越权、HTTP/CSRF、恢复、未知回执、取消、重启、同一 Codex 会话续处理、并发队列、源码基线和测试失败。
- `tests/incident-verifier.test.ts`：实际 Docker 隔离执行及受保护测试防改写。
- `scripts/incident-live-smoke.ts`：真实 Codex 修复临时 `sum.js`，继续同一 thread，独立 Docker 测试；保留原始源码。
- `scripts/incident-preview.ts`：独立临时数据的 UI 夹具，原生聊天区域为占位页，不能当作生产原生容器验收。

现有常规聊天统计不计入报障。正式部署另需检查实际项目的独立验证镜像、主机配置和 Codex 登录，结果见当次部署记录。测试夹具不能替代真实供应商故障恢复与成员视频加载的联合验收；本模块不等于完整无人值守运维。
